# Damat module starter — `module-sample`

> The clone-to-start reference for a Damat module: one model, a CRUD-only
> service, and a fully **generated** route → workflow → step slice — minimal but
> complete and current.

A Damat **module** is a self-contained vertical slice of a backend — its own
models, migrations, service, config, workflows, and routes — that plugs into any
Damat app. This folder is a working example of that shape; copy it, rename it,
and fill it in. See [`AGENTS.md`](./AGENTS.md) for the full authoring guide.

You develop and test the module **standalone** (it ships its own dev server and
test harness), then it **leaves**: install it into a backend with
`damat module add <path>`, which **splits** it across the app — the model/service/
types stay under `src/modules/<name>/`, while the generated routes and workflows
move to where the framework actually mounts/runs them.

## The layering (the rule)

```
API route  ─calls→  Workflow  ─orchestrates→  Step(s)  ─call→  Service (CRUD + integrations)
```

- **Service** = bare CRUD for each model (from `ModuleService`) **plus** any
  third-party integration (the SDK import + calls live in `src/lib/`). Reachable
  **only from steps**, via the typed `getModule("module-sample")`.
- **Step** = one unit of work with a compensation/fallback (directly callable).
- **Workflow** = orchestrates steps. **Route** = calls a workflow.

`codegen` generates this whole slice from your models — **scaffold-once**, so your
edits to steps/workflows/routes survive regeneration. Types + zod + `registry.ts`
are always rewritten.

## Use it

```bash
cp -R module-sample ../my-new-module     # clone
cd ../my-new-module
# rename: package.json name, src/module.json name, MODULE_ID + class in src/index.ts & service.ts
bun install
bun run migration:create                 # diff models -> SQL migration
bun run codegen                          # types + zod + registry + CRUD scaffold
bun run validate                         # contract + registry readiness (aim for no warnings)
bun run dev                              # run the module standalone (its own server + /health)
bun test                                 # contract test always; service test when DATABASE_URL is set
```

## What's inside

```
module-sample/
├── package.json          # direct @damatjs/* deps (services, framework, orm-model, workflow-engine, deps, module)
├── tsconfig.json         # self-contained strict TS config
├── module.config.ts      # the only module-custom setup (e.g. dev port)
├── .env.example          # DATABASE_URL + the example credential
├── AGENTS.md             # the authoring guide for this module
└── src/                  # ← this is what gets split into a backend on install
    ├── module.json       # the portable manifest (name, env, registry, pairsWith)
    ├── index.ts          # defineModule(...) — registry typing is generated, not hand-written
    ├── service.ts        # ModuleService; models = collectModels([ItemModel]) — CRUD + integrations only
    ├── lib/              # (optional) third-party SDK code (one file per provider) called by the service
    ├── utils/            # (optional) small pure helpers, one concern per file
    ├── config/           # zod credentials schema + (env) => credentials loader
    ├── models/           # ORM models (one example: item -> table `items`)
    ├── types/            # GENERATED: row types + zod + registry.ts
    ├── workflows/items/  # GENERATED: per-operation steps + callable-step workflows (scaffold-once)
    ├── api/routes/items/ # GENERATED: split routes (api/validator/query/middleware/route) (scaffold-once)
    └── migrations/       # generated by `migration:create`
```

Each folder under `src/` carries its own README. They are teaching aids — delete
them once the skeleton becomes a real module.

## Rules that keep a module portable

- **Import from the real packages** (so the code fits unchanged when installed):
  `defineModule`/`ModuleService` ← `@damatjs/services`, `getModule` ←
  `@damatjs/framework`, `model`/`columns`/`collectModels` ← `@damatjs/orm-model`,
  workflow helpers ← `@damatjs/workflow-engine`, route types ←
  `@damatjs/framework/router`, `z` ← `@damatjs/deps/zod`. `@damatjs/module` itself
  is only the contract/config/runtime/tooling.
- **No cross-module internals:** a module never defines links or imports another
  module; store foreign ids as plain columns. Composition is the app's job — leave
  a non-binding `pairsWith` hint in `module.json` if it pairs with something.
- **The table name is the source of truth:** `collectModels([...])` derives the
  service accessor (`service.items`) from the model's table name.
- **Codegen-first — don't hand-write CRUD.** Model the data, run `codegen`, get the
  whole route → workflow → step slice, then extend it (logic in steps, custom
  workflows, integrations on the service). A **route only calls a workflow** — never
  the service, never business logic; the **service is CRUD + integrations only**.
- **No big files.** Distribute code: one model per file, one integration per
  `src/lib/<provider>.ts`, helpers in `src/utils/`.
- **Env only via `config/load.ts`**, declared in `module.json#env`.
- **Migrations are append-only** once published.

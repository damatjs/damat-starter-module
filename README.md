# Damat module starter — `module-sample`

> The clone-to-start template for a new Damat module: one model, one service, one route, config, and a test — minimal but complete.

A Damat **module** is a self-contained vertical slice of a backend — its own
models, migrations, service, config, workflows, and routes — that plugs into any
Damat app. This folder is a working example of that shape; copy it, rename it,
and fill it in.

You develop and test the module **standalone** (it ships with its own dev server
and test harness), then it **leaves**: drop the folder into the
[`modules/`](../modules) monorepo under `packages/<name>`, or install it straight
into a backend with `damat module add <path>` (which copies its `src/` in). The
framework is consumed as published `@damatjs/*` npm packages (`^0.1.1`) — it is
not vendored here.

## Use it

```bash
cp -R module-sample ../my-new-module     # clone
cd ../my-new-module
# rename: package.json name, src/module.json name, MODULE_ID + class in src/index.ts & service.ts
bun install                              # (add --minimum-release-age=0 if a needed release is <2 days old)
bun run migration:create                 # diff models -> SQL migration
bun run codegen                          # generate row types + zod schemas
bun run validate                         # contract + registry readiness (aim for no warnings)
bun run dev                              # run the module standalone (its own server + /health)
bun test                                 # contract test always; service test when DATABASE_URL is set
```

## What's inside

```
module-sample/
├── package.json          # @damatjs/* deps at ^0.1.1; module scripts
├── tsconfig.json         # self-contained strict TS config
├── module.config.ts      # the only module-custom setup (e.g. dev port)
├── .env.example          # DATABASE_URL + the example credential
└── src/                  # ← this is what gets inserted into a backend
    ├── module.json       # the portable manifest (name, env, registry metadata)
    ├── index.ts          # defineModule(...) + ModuleRegistry augmentation
    ├── accessor.ts       # typed getModule() helper for routes/steps
    ├── service.ts        # ModuleService({ models, credentialsSchema }) + methods
    ├── config/           # zod credentials schema + (env) => credentials loader
    ├── models/           # ORM models (one example: item)
    ├── api/routes/       # file-based HTTP routes (example: items)
    ├── workflows/        # sagas (empty placeholder)
    ├── migrations/       # generated by `migration:create`
    └── types/            # generated by `codegen`
```

Each folder under `src/` carries its own README explaining what lives there and
how to extend it. They are teaching aids for the template — delete them once the
skeleton becomes a real module.

## Rules that keep a module portable

- **One import:** module `src/` imports only `@damatjs/module` (plus generated
  `@damatjs/deps/zod` in codegen output).
- **No cross-module internals:** reference other modules by id (in
  `module.json#modules`) and store foreign ids as plain columns — no FKs across
  modules.
- **Env only via `config/load.ts`**, declared in `module.json#env`.
- **Migrations are append-only** once published.
